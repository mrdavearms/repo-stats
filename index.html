What these numbers can and cannot tell you

  • Installer downloads counts every time GitHub served an installer file (.exe, .msi, .dmg and similar). GitHub does not record who downloaded, so there is no unique figure. One person who downloads twice counts twice. A Windows copy that updates itself counts once more, because the updater fetches the new installer. Security scanners and web crawlers count too. GitHub sometimes revises a count downwards a day later, which shows as a negative day.
  • Suspected automated bursts are days when one repo gained at least 15 downloads and at least 8 times its usual day. Every burst so far has looked like a crawler, not people: on 27 May 2026 one 600 MB Mac installer of Doc Redactor was fetched 92 times in a day, and on 10 Jul 2026 every Mac installer of Bulk PDF back to v2.7 gained exactly one download on the same day. The "excluding bursts" figure replaces each burst day with a typical day.
  • Update checks counts fetches of the small manifest file (latest.yml or latest.json) that an installed copy reads when it checks for a new version, usually once per launch. It is the best available sign that copies are installed and in use. It is a count of checks, not of computers. Only Doc Redactor and NAPLAN publish such a file. Bulk PDF checks for updates with a lightweight request to its releases page, which GitHub does not count anywhere, so its update checks cannot be measured.
  • Page views and unique visitors come from GitHub's traffic data, which only covers the last 14 days at any time. GitHub counts unique visitors per day, so the daily sum counts a person once for every day they visited.
  • Clones are almost all automated: mirrors, search indexers and build systems. Clones running many times higher than page views are not people.
  • NAPLAN (source) shows zero downloads by design. Its releases are drafts; the public installers and their counts live under NAPLAN (downloads).
